## 1. 画面・シーン構成

### 1-1. 共通部品 `BackgroundMoon`（F5・F14）

月は **1 つの共通シーン `core/presentation/background_moon/background_moon.tscn`**（スクリプト `background_moon.gd`、`class_name BackgroundMoon`）にまとめ、3 画面の `.tscn` が**それぞれ 1 ノードを足す**（コードの重複は無い）。置き場を `core/presentation` にするのは、3 つのコンテキスト（auth・login・player）が使うため。別コンテキストの presentation のシーンは参照できない（architecture 2 節の「他コンテキスト」）が、`item_icon`・`SafeAreaMargins` の前例どおり `core/presentation` は全コンテキストから使える。

```
<画面のルート Control>
├── BgVideo            既存。ここは触らない（動画は 1-2 の再生成で月なしになる）
├── BackgroundMoon     新規。BackgroundMoon のインスタンス。BgVideo の直後（画面の他の部品より下）
│   ├── FogLight       ColorRect。霧の月明かり（F13）。加算合成のシェーダー
│   ├── Glow           ColorRect。月の光のにじみ（F13）。加算合成のシェーダー
│   └── Moon           ColorRect。月の本体（満ち欠け・暗い側の輪郭。F7・F9）
└── （各画面の UI。今までどおり）
```

- `BackgroundMoon` 自身は全面の `Control`（`anchors_preset = 15`）で `mouse_filter = IGNORE`。子 3 つも `IGNORE`（タップを奪わない。ログインボーナスの `TapBg` などに影響しない）
- **描く順は BgVideo → FogLight → Glow → Moon → UI**。UI は今までどおり月の上に出る（U-7: UI が月を隠す画面があっても、F14 のとおり同じ月を出す。隠れ方の確認は S5 の録画）
- 3 画面の差分は `.tscn` に `BackgroundMoon` を 1 つ足すことだけ。`login_bonus_from_home.tscn` は基底を継承しているので、基底に足せば両方の入口に出る（0 の c）。presenter は変えない

### 1-2. 動画と月の位置・倍率を合わせる方法（U-5）

0 の b のとおり、`BgVideo` は「ルートの矩形」に全面で張られ、動画をその矩形へ引き伸ばす。月を**同じ矩形（= `BackgroundMoon` 自身の矩形）の割合で置けば、動画と必ず同じ座標系**になる。

- 位置: 矩形の幅・高さに対する割合。中心 = `(0.78 * 幅, 0.115 * 高さ)`（今の月と同じ。要件「現状の調査」）
- 半径: **幅に対する割合**（`125 / 1080` × 幅）。1080 のときちょうど 125px。縦横比が違う矩形になっても円は円のまま（動画の引き伸ばしと完全には一致しないが、現状は 1080x1920 固定で等倍。下の注）
- `BackgroundMoon` が `resized` を受けて、子 3 つの矩形とシェーダーの値（中心・半径をピクセルの割合で渡す）を更新する。値の持ち方は割合なので、矩形の大きさが変わっても追従する
- 現状は `aspect = keep` でビューポートが常に 1080x1920 なので、**画面比率が違う端末でも動画と月はずれない**（余白は黒帯）。将来 `aspect` を `expand` などに変えるときは、動画が引き伸ばされる一方で月の半径は幅基準になるので、その時点で見直す（未解決点 U-5 に残す）
- 実機の異なる比率（例: 4:3 のタブレット、縦長の端末）での見え方の確認は S5。デスクトップでは `godot --path . --resolution 1080x1440 ...` のようにウィンドウの比率を変えて確かめられる（黒帯が出て月が動画に付いてくることを見る）

### 1-3. 描画方式（シェーダーで描く。ノードの組み合わせにしない）

**ノードの組み合わせ（`Polygon2D` や `TextureRect` の重ね）にせず、`ColorRect` + canvas_item シェーダーで描く。** 理由は 3 つ。(1) F9 の連続した満ち欠けは、式 1 つで滑らかに決まる（形ごとの絵や頂点を持たない）。(2) 縁のぼかし・暗い側の輪郭・光のにじみは、式でそのまま書ける。(3) 値は画面を開いたときに 1 回渡すだけで、毎フレームの再計算が無い（非機能）。

| 子 | シェーダー（置き場 `core/presentation/background_moon/`） | 描くもの | 合成 |
| --- | --- | --- | --- |
| `Moon` | `moon.gdshader` | 円の内側を、暗い側（薄い一定の色）と明るい側（月の色）に塗り分ける | 通常（アルファ） |
| `Glow` | `halo.gdshader` | 月の中心から半径 `1.7r` のガウス型 `exp(-(d / 1.7r)^2)` の光 | 加算 |
| `FogLight` | `halo.gdshader`（同じシェーダー。半径・色・強さの値だけ違う） | 月の中心から半径 380px（幅 1080 のとき）のガウス型の光 | 加算 |

**月の本体（`moon.gdshader`）の式**: 月の円の中の点を、半径で正規化した座標 `(x, y)`（`x` は右が正、円の中は `x² + y² ≤ 1`）にする。`c = cos(2π * 位相)`（位相は 3 節。新月 0・満月 0.5）、`向き = +1`（右が光る）か `-1`（左が光る）とする。

- 明るい側 = `向き * x > c * sqrt(1 - y²)` を満たす点
- 新月（位相 0、`c = 1`）: どの点も満たさず、明るい側は無い。上弦・下弦（位相 0.25・0.75、`c = 0`）: `x` が向き側の半分。満月（位相 0.5、`c = -1`）: 円全体が明るい。**この式は位相に対して連続**（F9）で、境目は楕円（満ち欠けの終端線）になる
- 縁は円の外周を約 1.5px ぼかす（今の月の縁と同じ。0 の h）。**明暗の境目は硬い線にせず、`terminator_soft`（0.30。人が『強い版』の境界を採用）の幅のやわらかい陰影のグラデーションにする**（人の決定。2026-11-22。半月が硬い線だけで味気ないため）。半月まわりはこの幅のまま、|cos(位相)| が 0.5 を超える細い三日月・満月・新月の近くだけ自動で狭め、細い三日月が陰影で消えないようにする。満月・新月では境目が外周と重なるので、位相が近づくにつれ境目の位置をなだらかにずらして、外周に明暗の縁取りが出ないようにする
- 暗い側は**完全には消さず**、薄い**地球照**（青みがかった弱い光。色 (0.60,0.68,0.92)・アルファ 0.10）で円全体を描いておく（F7。新月でも位置が分かる輪郭になる）。旧設計の「月の色と同じ系統・アルファ 0.10」を置き換えた（A-6 の更新）
- **月面の模様と周縁減光（人の決定。2026-11-22。控えめに）**: 向きを固定したノイズ（p だけで決まり、満ち欠けで動かない）で、海（大きな暗い斑）・細かい濃淡・クレーター 2 つを、かすかに分かる程度だけ足す。縁に向かってわずかに暗くする（周縁減光）。強さはすべて `moon.gdshader` の uniform（`maria_strength`・`mottle_strength`・`crater_strength`・`limb_darkening`・`earthshine_alpha`・`terminator_soft`。名前とコメント付き）で、人が 1 行ずつ調整できる。旧三日月の白くすっきりした印象を保つ中間を狙った（一度つけた強い模様は「リッチすぎる」で弱めた）
- 明るい側の色は今の月と同じ (250,250,255)（F4）。大きさ・位置は 1-2 のとおり

**光のにじみ・霧の月明かり（F13）**: 強さを「照らされている割合 `illumination`」（3 節。新月 0・満月 1）に**比例**させる。にじみは今の動画の式（`img += ガウス * 0.28 * 色(150,150,190)`、半径 1.7r）が加算なので、加算合成で `0.28 * illumination` にすれば、満月で今と同じ強さ、新月でほぼ消える。**霧の月明かりは同じ扱いにできない**（下）。

- **霧の月明かりの旧実装と、再現の限界（U-6）**: 旧実装（`generate_bg_video.py` の `FogLayer`）は、月の中心から半径 380px のガウス `glow`（中心で 0.75）を使い、`rim = glow * (明るい色(205,205,235) - 雲の色)` を雲の色に足した色を作り、それを**雲の不透明度 `a` で空へ混ぜる**（`region += (雲の色 + rim - region) * a`）。つまり **雲のある所だけ**が明るい色へ寄り、**雲の無い空は変わらない**。『強さ 0.75 の加算光』ではない。同じ式を全面の加算光にすると、月の中心で約 +154/255 の光の塊になり、雲の無い空まで明るくなって誤り
  - 既定案: 重ね描き側は雲の位置・濃さを知らないので**追従できない**。そこで、月まわりの柔らかい光（ガウス。色 (205,205,235) 寄り）を、**旧動画の雲の平均的な被り具合に相当する弱い係数**で足す近似にする。**係数は 0.75 ではなく、S5 で旧動画（月明かり入り・git の履歴から取り出す）と新しい合成を同じ時刻のコマで見比べて決める**（強さは `illumination` に比例させる）。許容できるかは人が見る。この近似の違いは次の 2 つ。(1) 雲の動きに合わせた明るさの揺れが無くなる。(2) **旧動画では雲の層が月の手前を覆って横切っていたが、重ね描きの月は雲より前に描かれるので、雲が月の前を横切らなくなる**（月がいつもくっきり見える。見た目が変わる点として人に見せて決める）
  - 採らない案（記録）: 画面テクスチャ（`hint_screen_texture`）を読んで、動画の明るさに応じて強める方法。雲に追従できるが、モバイルで毎フレーム画面のコピーが要り、負荷の基準値が無いので採らない（足りなければ後の改善）
- にじみの加算の色は光の色に `強さ * ガウス` を掛けたもの（今の動画は `img += glow * 0.28 * 色` と加算で焼いているので、加算合成で同じ式になる。霧の月明かりには当てはまらない）

**負荷**: ノードは `ColorRect` 3 枚。値（位相・向き・強さ・中心・半径）は画面を開いたとき（と `resized`）にだけ設定し、`_process` は持たない（毎フレームの再計算なし）。光の 2 枚は矩形をガウスが十分小さくなる範囲（半径の **3 倍**以上。2.2 倍で切るとガウスが約 0.8% 残って矩形の縁に縞が出るため、さらに縁の手前で 0 へなめらかに落とす係数を掛ける）に収めて、塗る面積を抑える。実機の負荷は 7 節。

## 3. 満ち欠けの計算（F2・F9・F12）

**平均朔望月による近似を採る**（天文学的な厳密さは対象外。F12 の約 1 日以内を満たすことが目的）。

- 定数（`MoonPhase` に置く）: 朔望月の平均 `SYNODIC_DAYS = 29.530588853` 日、基準の新月 = **2000-01-06 18:14 UTC**（UNIX 秒 947182440。一般に使われる平均の新月の基準）
- 月齢（日）= `fposmod((unix - 基準) / 86400, SYNODIC_DAYS)`（0 以上 29.53 未満。新月が 0）。秒まで反映した連続値（F12）
- 位相 = 月齢 / `SYNODIC_DAYS`（0〜1。0 と 1 が新月、0.5 が満月）
- 照らされている割合 `illumination = (1 - cos(2π * 位相)) / 2`（新月 0、上弦・下弦 0.5、満月 1。連続）。F13 のにじみ・霧の強さと、月の見た目の明るい面積の両方がこれに従う
- 満ちていく途中 `waxing` = 位相 < 0.5（新月 → 満月）。欠けていく途中は位相 ≥ 0.5
- 光る側 `lit_on_right` = 北半球なら `waxing`（満ちていく間は右、欠けていく間は左。F10）、南半球は反転（F8）。1-3 の `向き` はこの値（右 = +1、左 = -1）
- 見た目の基準（F10）: 今の三日月は北半球の夕方の若い月（月齢 3 日前後）に当たる。この設計では**形は満ち欠けの式が決める**ので、月齢 3 日（位相 0.10、`illumination ≈ 0.1`（式で約 0.098））では右側が細く光る三日月になる。今の焼き込みの形（円を円で引いた三日月）と一致させることは目指さない（F4 が維持するのは位置・大きさ・色・にじみ。要件の体験 4）

### 3-1. 精度の根拠（F12）

平均朔望月は、実際の新月・満月の時刻から**最大で半日強（目安 0.6 日前後）**ずれる（月の軌道が楕円で、実際の朔望月が 29.27〜29.83 日の間で伸び縮みするため。ここは天文学の一般知識で、この文書では導出しない）。これは要件が許容する「約 1 日以内」の範囲内。

**参考値で確かめた**（記憶にある新月・満月の日時と式の比較。権威ある暦で引いた値ではないので、**S5 の単体テストでは暦の出典を付けた値を使う**。これは確認できていない点）:

| 実際の出来事（UTC。記憶による） | 式の月齢（日） | 本来 | 差 |
| --- | --- | --- | --- |
| 2024-04-08 18:21 新月 | 29.36 | 0（= 29.53） | 約 -0.17 |
| 2024-12-30 22:27 新月 | 0.22 | 0 | 約 +0.22 |
| 2024-04-23 23:49 満月 | 15.06 | 14.77 | 約 +0.30 |
| 2025-01-13 22:27 満月 | 14.22 | 14.77 | 約 -0.55 |

最大でも 0.6 日未満で、見た目（光る面積）の差は小さい。さらに精度が要るときは、主要な周期項を足す（後の改善。この設計では足さない。F12）。

### 3-2. 画面への反映のタイミング（F11・非機能）

`BackgroundMoon._ready` で 1 回計算し、`apply` で値を設定する。以降は再計算しない。開いたまま日をまたいでも更新しない（要件の決定。overview 8.3）。次に画面を開く（遷移する）と、そのときの現在から決め直す。

### 3-3. 月の傾き（F16。人の決定 2026-11-22。要件の旧「対象外: 月の傾き」を変更）

「半月の境界が完全に上下で不自然」という指摘で、**空での月の明るい縁の向き**を時刻から近似して反映する。位置情報は使わない。実装は `core/domain/moon/moon_tilt.gd`（`MoonTilt`。純関数）。結果は `BackgroundMoonView.tilt_radians`（明るい縁の向きを、基準の向き［右が光るなら右・左なら左］から画面で反時計回りに回した角。-π〜π）。

- **仮定**: (1) 太陽と月の赤緯は 0（天の赤道上）。季節・月の軌道の傾き（約 5 度）は無視 (2) 観測緯度は固定で、**北半球の見え方は北緯 35 度、南半球は南緯 35 度**（半球は 4 節の判定。判別不能は北） (3) 経度は現地時刻から近似する: 現地の太陽時 = UTC + タイムゾーンの差（`TimeZoneSource.bias_minutes()`）。夏時間を含む時計のずれ・均時差は無視（最大で 1 時間強 = 15 度ほどのずれ）
- **式**（観測者の座標 x=東・y=北・z=天頂、緯度 φ）: 赤緯 0・時角 H の天体の向き `r = (-sin H, -cos H sin φ, cos H cos φ)`、時角が増える向き（赤道に沿った西向き）`w = dr/dH = (-cos H, sin H sin φ, -sin H cos φ)`。月の位置で見た画面の上 `u` は天頂 z から r 方向の成分を引いて正規化した向き、右は `r × u`。太陽は月の東に離角 `E = 位相 × 360°` の所にあるので `H_月 = H_太陽 - E`、`H_太陽 = (現地太陽時 - 12 時) × 15°`。明るい縁は赤道に沿って太陽を向く: **満ちていく間（sin E ≥ 0）は w、欠けていく間は -w**。その向きの画面成分 `(d・右, d・上)` の角から、基準の向き（右 = +x・左 = -x）を引いたものが tilt
- 南半球は φ = -35° を入れるだけで、光る側の左右の反転も含めて物理的な見え方になる（`lit_on_right` は 4 節の判定のまま。tilt は基準の向きからの回転なので、反転しても連続）
- **検算（北緯 35 度。単体テストで許容幅つきで確認）**: 上弦が南中する 18 時は tilt ≈ 0（境界は上下・右が光る）。同じ上弦の 21 時は tilt ≈ -45°（右が下がる）。15 時は逆向き（+）。宵の三日月（新月後 3 日・19 時）は約 -53°（右下を向く）。明け方の下弦の 6 時は南中で tilt ≈ 0（左が光る）。南半球の上弦 21 時は北半球と大きさが同じで符号が逆。満月・新月は値が連続で任意（見えない）
- **描画**: `moon.gdshader` の `tilt` で、明暗の境目（`edge = a - cos_phase * sqrt(1 - b^2)`。a は明るい縁の向きの成分、b は垂直な成分）だけを回す。**月面の模様・周縁減光は向き固定のまま**（回さない）。地球照は明暗の割合に従うので境目と一緒に回る
- **現地時刻の入力**: `GetBackgroundMoonUseCase` が、`MoonOverride.local_hour`（上書き）→ 時刻（`unix` の上書き、なければ `Clock`）+ タイムゾーンの差、の順で決める。`--e2e-moon-age` だけ指定しても現地時刻は現在のまま（録画で再現するには `--e2e-moon-hour` を併用）
- **限界**: 赤緯 0 の近似・固定の緯度・平均太陽時の近似のため、実際の月の傾きとは数十度ずれることがある（高緯度・季節・月の軌道の傾きの影響）。時計が夏時間のときは 1 時間（15 度）進んだ時刻として扱う。月が天頂の真上にあるときは傾きなし（0）

## 4. 半球の判定（F8・U-1）

### 4-1. 取得できる情報の限界

0 の f のとおり、取れるのは **`bias`（現在の UTC からの差。分。夏時間込み）と `name`（略称。IANA 名ではない）**だけ。

- **IANA の名前（`Australia/Sydney` など）では判定できない**: 名前は略称で、IANA 名は返らない（macOS で確認。**Android・iOS・Windows で何が返るかは未確認**）
- 略称は地域をまたいで重複し、略称が無い地域は `-03` のような数字になる
- bias は同じ値が南北にまたがる（例: UTC+10 はオーストラリア東部〔南〕もロシア極東〔北〕も使う）。夏時間で季節ごとに値が変わる（シドニーは冬 +10、夏 +11）
- 場所そのもの（緯度）は使えない（位置情報は対象外）

### 4-2. 方法（名前の確定表 → オフセットの確定表 → それ以外は北）

比較した案と採否:

| 案 | 内容 | 採否 |
| --- | --- | --- |
| A | 名前（略称）だけで判定 | 略称が返らない・数字の環境で全て北になる。単独では採らない |
| B | bias だけで判定（多数派の側に倒す） | 同じ bias が南北にまたがるので、誤判定が出る。**南北の両方に人口がある bias は北に倒す**（要件の既定「判別できないときは北半球」）以外にできない。単独では採らない |
| **C（採用）** | **A と B の「確実な部分だけ」の組み合わせ**。判定は上から順に、最初に当たったもので決める。1. 名前の確定表に当たれば南。2. bias が「南半球にしか無い」オフセットの確定表に当たれば南。3. それ以外は**北**（判別できない・赤道付近・南北混在はここ） | 「確実に南と言えるものだけ南、迷ったら北」で要件の既定どおり。誤って南にする（確実でないものを南にする）ことが無い |

**確定表（`Hemisphere` が持つ。値は実装時に表とテストで固定する。ここは採用する規則と例）**:

| 表 | 内容 | 南と言える理由 |
| --- | --- | --- |
| 名前（略称）の確定表 | `AEST`・`AEDT`・`ACST`・`ACDT`・`AWST`（オーストラリア）、`NZST`・`NZDT`（ニュージーランド）、`CHAST`・`CHADT`（チャタム）、`LHST`・`LHDT`（ロード・ハウ）、`SAST`（南アフリカ・レソト・エスワティニ） | その略称を使う地域が全て南半球 |
| 名前が IANA 名の形（`/` を含む）のときの接頭辞 | `Australia/`・`Antarctica/` で始まる名前 | 該当地域が全て南半球。**IANA 名が返る環境があるかは未確認**で、返らなければこの行は使われないだけ（害は無い） |
| bias（分）の確定表 | +8:45（525）・+9:30（570）・+10:30（630）・+11:30（690）・+12:45（765）・+13:45（825）・+13:00（780）・-9:30（-570） | このオフセットを使う地域（オーストラリアの一部・ロード・ハウ・ノーフォーク・チャタム・トンガ・サモア・トケラウ・マルケサス）が全て南半球。端数の分を持つオフセットはほぼ地域が限られる |

- **bias の確定表に入れないもの**（南北どちらにもある・判別が難しいもの）: +10:00・+11:00・+12:00（オーストラリア東部・ニュージーランドは南だが、ロシア極東・マリアナなどは北）、-3:00（ブラジル・アルゼンチンは南だが、ギアナ・グリーンランドの一部は北）、+2:00・+1:00・+7:00 など。**名前が確定表に当たらない環境（略称を返さない・数字の略称）では、これらは北になる**（限界として明記）
- 北半球の夏時間と南半球の夏時間は逆になるが、判定は bias の値ではなく**表への一致**だけなので、夏時間の有無は結果に影響しない（ただし南の冬は bias が +12:00 などに戻るため、略称が使えない環境では判別できない）

### 4-3. 限界（文書に明記する。実装後も README でなくこの節が正）

1. **南半球の主要な地域のうち、UTC+10・+11・+12・-3:00 の地域（オーストラリア東部・ニュージーランド・ブラジル・アルゼンチンなど）は、略称が使える環境でないと北のままになる**。略称が使えるか（`AEST` など）は端末の OS に依る。**Android・iOS の返り値は未確認**（実機が無い。S5 の実機確認、または人が持つ端末）
2. 赤道付近・南北混在（インドネシア・ケニアなど）は常に北（要件のとおり）
3. 端末のタイムゾーン設定が旅行先や手動設定のときは、その設定のまま判定する（補正しない）
4. 判定は端末の**現在の**タイムゾーンで行い、録画で日付を指定しても変わらない（半球は 5 節の引数で上書きする）

人が判断する余地（未解決点 U-1a）: 2 の「ブラジルなど -3:00 を南と決めてしまう」案。人口の多い地域を拾えるが、ギアナなどを誤って南にする。**既定案は採らない（北に倒す）**。

## 5. 録画・e2e の引数（F15・U-4）

既存の命名（`--e2e-` 始まり）に合わせ、`E2EDriver` が読んで `AppContext.debug_moon_override()` に設定する（`--e2e-clock-skew` と同じ仕組み。ドライバーはメインシーンの `_ready` より前に動くので、画面が開く前に設定が済む）。**製品ビルドでは E2EDriver が動かず（debug ビルド限定。既存の仕組み）上書きは空のまま**。

| 引数 | 値 | 意味 |
| --- | --- | --- |
| `--e2e-moon-date=<日付>` | `YYYY-MM-DD` または `YYYY-MM-DDTHH:MM`（**UTC**。末尾に `Z` は付けない） | その時刻の月を出す。**時刻を省くと 12:00 UTC**（日付の真ん中。その日のどこで開いても月齢の差が半日以内に収まる）。日本の夕方（20:00 JST = 11:00 UTC）を撮りたいときは `T11:00` と書く |
| `--e2e-moon-age=<日数>` | 0 以上 `29.53` 未満の小数 | 月齢を直接指定する（**仮置きの追加**。F15 は日付だけだが、新月・上弦・満月・下弦をぴったり撮るには日付では 1 日単位のずれが出るので足す）。`--e2e-moon-date` と同時に指定したら**エラー**（どちらが効くか曖昧になるため） |
| `--e2e-moon-hour=<時>` | 0 以上 24 未満の小数 | 傾き（3-3）の計算に使う**現地の太陽時**を直接指定する（録画で「18 時の上弦」を撮るため）。指定しなければ時刻 + タイムゾーンの差 |
| `--e2e-moon-hemisphere=north\|south` | `north` か `south` | 半球を指定する。指定しなければ 4 節の判定 |

- 指定しなければ、現在の時刻（`Clock`）と、タイムゾーンからの推定（F15）
- 値が不正（日付の書式・範囲、月齢の範囲、半球の値、date と age の同時指定）のときは、`E2E_RESULT: FAIL bad-moon-arg <理由>`（終了コード 1）で起動直後に止める（録画で黙って別の月が出るのを防ぐ）
- 解釈は `E2EDriver` の静的関数（既存の `clock_skew_seconds` と同じ形）にして単体テストできるようにする。日付の変換は純関数にして `MoonOverride` に UNIX 秒を渡す
- `E2E:` の行に、画面が出たときの月の値を 1 行出す（`E2E: moon age=… phase=… illumination=… lit=right|left hemisphere=north|south`。書式は実装で確定。`age` は小数 2 桁・`phase` と `illumination` は 3 桁。末尾に ` tilt=<度。小数 1 桁>`）。**ドライバーが画面のノード名で探す方式は結合が強いので採らない**。代わりに、`GetBackgroundMoonUseCase` が計算した `BackgroundMoonView` を、デバッグ観測用に `MoonOverride.last_view` へ書き込む（判定には使わない。保存しない D-3 とは別で、製品では誰も読まない）。ドライバーは `AppContext.debug_moon_override()` を介して読み、画面が変わったときに 1 行出す。画面のノード構成に依らない。録画の期待値の照合に使う
- 実機に近い確認として、**タイムゾーンは OS の環境変数でも変えられる**（macOS で `TZ=Australia/Sydney godot ...` が `Time.get_time_zone_from_system()` に反映されることを確認済み。0 の f）。南半球の判定の全体（取得 → 判定）を、引数の上書きなしで通す確認に使う（11 節）

## 6. 動画の再生成（F1・F6・U-2）

### 6-1. 外すもの（生成スクリプトの変更方針）

- **月以外は変えない**（グラデーション・雲・星・流れ星・ディザ）。月・にじみは乱数を使わないので（0 の h）、削除しても星・雲・ディザの乱数の並びは変わらず、**月まわり以外の見た目は同じ**になる
- モジュール冒頭の説明文と `docs/ASSETS.md` の記述（「…月…を numpy で描いて生成」「約 2MB」）を、月を描かないことと、月は実行時に `core/presentation/background_moon` が描くことに直す。重ね描き側の位置・半径・色の値（今の月の値）は**このスクリプトの旧値が由来**であることを、`BackgroundMoon` 側のコメントに書く（数値の元を残す）
- 動画の外形（1080x1920・25fps・20 秒・音声なし・ループ・固定の乱数の種）は変えない

### 6-2. 誰がどの環境で作り直すか・再現の検査（U-2）

- **S5 の実装者が、この環境（macOS。`clang`・`ffmpeg`・theora を確認済み。`brew install theora` が要る）で 1 回作り直し、`assets/video/bg_loop.ogv` をコミットする**（現行と同じ運用。動画は生成物だがコミットしている）
- CI で再生成して一致を検査することは**しない**（Theora のエンコード結果が libtheora の版・環境で完全に一致するかは未確認。一致しなければ CI が不安定になる）。代わりに、**再生成のたびに次の 2 つを人手の手順で確かめる**: ① 容量が 2,028,637 B 以下、② 月の位置（中心 `(842, 221)`・半径 125px の円の内側と周辺）に月・光のにじみが無いこと（`ffmpeg` で数コマ抜いて、月の中心の色が同じ高さの空の色と同じであること。11 節）
- 「月・にじみ・霧の月明かりが動画に残っていない」ことは、生成スクリプトの単体テストでも確かめる（軽い Python のテスト。`make check-deps` に含める既存の `tools/tests/` の形）: 小さな解像度でベースの画像を作り、月の位置の画素が同じ縦位置の左端の画素と同じ（ディザの揺れの範囲）であること。**テストを足す場合のみ**。足さない場合は上の人手の確認で足りる（S5 で判断。仮置き A-3）

### 6-3. 容量

月を外した動画は、現行（2,028,637 B）以下にする（非機能）。月と光のにじみの分の画素の変化が減るので増えない見込み。**増えた場合**は、`--bitrate`（既定 800000）を下げて再生成し、見た目を確かめる（上限を超えない範囲で）。再生成後の実測値を `docs/ASSETS.md` の記述に反映する。

## 実装で決まった値（第 2 段）

- 霧の月明かり `FOG_STRENGTH` = 0.05（根拠は A-4）。光のにじみは 0.28・色 (150,150,190)、霧は色 (205,205,235)・ガウス 380px（幅 1080 のとき）
- 見た目の強さ（`moon.gdshader` の uniform。人が最終判断）: 地球照 `earthshine_alpha` = 0.10・色 (0.60,0.68,0.92)、境目のやわらかさ `terminator_soft` = 0.30（境界だけ強い版を採用。細い三日月・満月・新月の近くは自動で狭まる）、月面の模様 `maria_strength` = 0.05・`mottle_strength` = 0.015・`crater_strength` = 0.04、周縁減光 `limb_darkening` = 0.07。『リッチすぎる』の指摘で、最初の強い版（地球照 0.16・模様 0.26・0.10・クレーター 0.25 相当・周縁減光 0.22）から弱めた（境界の 0.30 だけは強い版のまま）
- `E2E:` の月の行の書式: `E2E: moon age=7.38 phase=0.250 illumination=0.500 lit=right hemisphere=north`（月のある画面が出るたびに 1 行。規約画面では出さない）
- `--e2e-moon-*` の解釈は `E2eMoonArgs`（`debug/e2e_moon_args.gd`）に分けた（`e2e_driver.gd` の行数上限のため）。テストは `tests/unit/debug/e2e_moon_args_test.gd`
- 3 画面の構成テスト（`tests/unit/core/presentation/background_moon/background_moon_test.gd`）: 4 つの `.tscn`（ログインボーナスは両入口）に `BackgroundMoon` が 1 つだけあり、`BgVideo` の直後で、アンカー・オフセットが `BgVideo` と一致する
- 動画は 1,869,429 B で再生成済み（6-3 の上限 2,028,637 B 以下）
